# UI Batch (C1-C6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the six owner requests C1-C6 from the HANDOFF.md Task board:
- themed confirm dialog;
- route line only after Optimize, with distinctive stop markers;
- search bar joined to the header;
- monochrome weather icons;
- Safari-friendly downloads;
- a "My trip" tab that holds the itinerary and Priority, with Stops slimmed down to a name and a rounded photo per row.

**Architecture:**
- One shared `Dialog` primitive (a portal with a focus trap) serves the delete confirmations (C1) and the PDF download dialog (C5).
- A per-trip "optimized" marker is stored in a new nullable column, `Trip.routeOptimizedFor`. It holds a signature of the stop configuration, so it survives reloads and turns false by itself whenever that configuration changes. It drives the My trip view (C6) and whether the route line is drawn (C2).
- Weather lines carry a `sky` kind instead of an emoji, and a `WeatherIcon` SVG draws the icon (C4).

**Tech Stack:** Next.js 16 (App Router), React 19, TypeScript, Tailwind v4 (tokens in `src/app/globals.css`), Prisma 7 with SQLite/Turso, Zod, Mapbox GL, dnd-kit, jsPDF, Vitest with Testing Library, Playwright (fake map, `EXTERNAL_APIS_FAKE`).

**Spec:** HANDOFF.md Task board rows C1-C6, plus three owner updates to C6 relayed by the coordinator on 2026-10-18:
1. The Priority pill moves to My trip.
2. Stops rows show only the name and a photo.
3. That photo has rounded corners.

### C1: the confirm dialog
- `role="alertdialog"`, which keeps the existing `getByRole("dialog", { name: /^Edit / })` StopDrawer queries unambiguous. It also has `aria-modal="true"`, `aria-labelledby` (title) and `aria-describedby` (message).
- It renders through `createPortal(…, document.body)` with a fixed overlay `bg-black/40`. It does not use `<dialog>.showModal()`, which jsdom lacks.
- The card is `card` from styles.ts, plus `w-full max-w-sm p-5`. The overlay has `p-4`, so a 320 px screen keeps a 16 px gutter.
- Buttons are right-aligned and wrap:
  - Cancel uses `btnSecondary`.
  - Delete uses a new `btnDanger`: `bg-danger text-ink-foreground`. Contrast is #faf6ec on #a82a1e in light and #111111 on #f19a92 in dark, so both pass.
- Initial focus goes to **Cancel**, the safe choice. Tab and Shift+Tab wrap inside the card. Escape, or a press on the backdrop, cancels. Focus returns to the element that was focused before the dialog opened.
- Copy:
  - Trip: title `Delete trip?`, message `Delete "{name}"? This cannot be undone.`, button `Delete`.
  - Stop: title `Delete stop?`, message `Delete "{name}" from this trip?`, button `Delete`.
- These are the only two native dialogs (`grep -rn "confirm(\|alert(" src` finds only these). No `alert()` exists.

### C3: the search bar
- On every width, the wrapper changes from `top-3` to `top-0`.
- The SearchBar input changes from `rounded-2xl` to `rounded-b-2xl rounded-t-none`. Its `bg-surface` is the same token as the header's `bg-surface`, so the two join with no seam. The bar's `z-[15]` paints over the header's `shadow-sm`.
- Horizontal insets stay as they are.
- The phone rule `.mapboxgl-ctrl-top-right { top: 4rem }` becomes `top: 3.5rem`, because the bar now ends about 0.75rem higher.

### C4: weather icons
- **Kinds:** one icon for each existing `WeatherLabel`: Clear, Partly cloudy, Mostly cloudy, Overcast and Rain likely. The forecast model has only cloud, rain and temperature, so snow, fog, storm and wind cannot be told apart without new data. Adding weather codes is out of scope; record this in the C4 row notes.
- **Drawing:** icons are 16×16 inline SVGs with `stroke="currentColor"`, `fill="none"` and `aria-hidden`. They take the colour of their line: `text-muted`, or `text-sand` when the light is poor. That keeps them in the beige/brown theme in both modes.
- **Data shape:** `WeatherLine.text` loses the emoji and gains `sky`:
  - Text is `"18°C"`, or `"Typical 18°C"`, or `""` when the temperature is unknown.
  - `sky` is a `WeatherLabel`, absent for "Forecast not available yet".
- **Surfaces:**
  - StopCard, PlaceCard, SuggestionsPanel and the My trip rows render the line through `WeatherText`.
  - The share page shows no weather today and gets none added.
  - The PDF already writes the weather in words and does not change.

### C6: the optimized state (shared with C2)
- **Where it lives:** a new column, `Trip.routeOptimizedFor TEXT NULL`, in the DB.
  - It is exposed on the `Trip` DTO as `routeOptimizedFor?: string | null`. The field is optional so that old offline copies and test fixtures still type-check.
  - It is accepted in `tripPatchSchema` as `z.string().regex(/^v1:[0-9a-f]{16}$/).nullable()`.
  - The server stores the value as sent and never computes it.
- **What it holds:** `routeSignature(plannedDate, stops)` from the new `src/lib/route-signature.ts`.
  - `"v1:"` followed by 16 hex characters, a synchronous 64-bit hash (cyrb53 run twice with seeds 0 and 1, each output as 8 hex characters).
  - The hash input is `plannedDate`, then for each stop in order: `id`, `lat.toFixed(6)`, `lng.toFixed(6)`, `lightPref`, `priority` and `dwellMinutes`.
- **How it persists:** the column is the persistence, so the state survives reloads, devices and the offline copy.
- **The derived flag:** in TripEditor, `optimized = stops.length >= 2 && trip.routeOptimizedFor === routeSignature(trip.plannedDate, stops)`. Because of this, the flag resets with no extra code on:
  - adding or removing a stop;
  - reordering, including drag and keyboard;
  - moving a marker;
  - swapping a stop;
  - changing a stop's priority, light or dwell;
  - changing the trip date.

  It does **not** reset on a start-time change, visited, notes, a rename or a photo. Undoing a change back to the exact optimized configuration counts as optimized again, which is correct.
- **When it is written:**
  - `optimizeRoute()` writes it in the same PATCH as `departAt`. This covers both the "Already the fastest order" and "No faster order found" outcomes; all of them mark the trip optimized.
  - The signature is computed over the **new** order.
  - Undo restores the previous value (`undo.previousOptimizedFor`).
  - Existing trips start un-optimized: the column is NULL.
- **Two stops:** with exactly 2 stops, Optimize is enabled. It skips `api.optimizeOrder`, because the server's minimum of 3 is unchanged and two stops have nothing to reorder. It only PATCHes `{ routeOptimizedFor }`. With 0 or 1 stops it is disabled.
- **Directions:** they are still fetched before Optimize, because suggestions and prewarm, the Export GPX/PDF and the arrival maths need them. They are just not drawn and not totalled until `optimized`.
- **Stale hint:** if `trip.routeOptimizedFor` is non-null but does not match, My trip shows the hint `Your stops changed. Optimize again to see the route.`.

### C6: the Stops rows (owner updates 2 and 3)
- `stop-row` shows **only** these, in order:
  - the rounded photo;
  - the name button, which opens the details and keeps class `truncate` plus the sr-only `{n}.` prefix, so `offline.spec` and screen readers still work;
  - the drag handle (`Reorder {name}`);
  - Delete (`Delete {name}`).
- It shows no number dot, visited toggle, times, weather, golden-hour text, priority, notes or role badge. Visited stays reachable from My trip, StopCard and StopDrawer.
- **Photo source** (new `StopPhoto`):
  1. `stop.photoUrl` (the user's own upload) if set.
  2. Otherwise `loadPlacePhoto({ key: \`stop:${lat.toFixed(5)},${lng.toFixed(5)}:${name}\`, name, lat, lng })`. That is the existing session cache, which keeps the in-flight promise, remembers a failure for 60 s, and never refetches a success.
  3. Otherwise a themed placeholder: a `bg-accent-soft` tile with a 16 px camera outline icon in `text-accent-strong`.
- **Size and shape:** the tile and the image are both `h-10 w-10 shrink-0 rounded-xl object-cover`. `rounded-xl` matches PlaceCard's thumbnail. The image also gets `bg-hover`.
- **Loading:** `loading="lazy"`, `decoding="async"` and `referrerPolicy="no-referrer"`.
  - The fetch starts only when the tile is on screen: an `IntersectionObserver` with `rootMargin: "200px"`. Where `IntersectionObserver` is undefined (jsdom), it starts at once.
  - Fetches happen only while the Stops tab is mounted.
  - An image `onError` drops to the placeholder.
- **Cost:**
  - Each stop costs at most one `/api/place-photo` call per session (cached by key). The route is already capped at 60/min per user and by `enforcePaidLimit` (paid sources Flickr/Commons; Flickr app budget 3000/h).
  - The trip is capped at 25 stops (MAX_ROUTE_WAYPOINTS), so the worst case is 25 calls, and lazy loading usually makes it fewer.
  - A 429 resolves to `null`, which gives the placeholder.
  - No new limits are needed.
- **Alt text:** `alt=""`. The photo is decorative and the name is right beside it, so a screen reader hears the name once.
- **320 px:** 16 px gutters, then a 40 px photo, a `gap-3`, the name with `min-w-0 flex-1 truncate`, the handle (`w-8`) and Delete (`w-9`). The name keeps more than 150 px.
- **Dark and light:** the radius and placeholder use tokens only. Check both modes visually.

### C2: the map
- `MapView` gets `routeGeometry={optimized ? activeRoute?.geometry ?? null : null}`. The Export menu still gets the real route (`activeRoute?.geometry`), so a GPX or PDF before Optimize still works.
- **Initial framing in MapPanel.** There is no route on first load now, so the map must frame the stops itself:
  - When `!fittedRef.current` and `routeGeometry` is null and there are at least 2 stops, fit the bounds to the stop coordinates once.
  - The existing route fit still applies when a route arrives and nothing was fitted yet.
- **Stop markers:** a new shared class, `STOP_MARKER_CLASS` in `src/lib/stop-style.ts`: `"flex h-8 w-8 items-center justify-center rounded-full border-[3px] border-white text-sm font-bold shadow-lg ring-1 ring-black/20"`.
  - The selected marker adds `ring-2 ring-route`.
  - Both MapPanel and FakeMapPanel use it.
  - Suggestion dots stay as they are: 14 px, `opacity-70`.
- The share page keeps its always-on route line. It is read-only and has no Optimize.
- FakeMapPanel's route `<polyline>` gains `data-testid="route-line"`, so e2e can assert it is absent before Optimize and present after.

### C5: downloads
- **Diagnosis:** the prompt appears because `saveBlob` runs after awaited work (weather 6 s timeout, map image, fonts, jsPDF import). By then the tap's user activation has expired, and Safari treats an anchor `download` click with no activation as an unrequested download.
- **Fix:** prepare first, then save from a fresh tap.
  1. "Download PDF" opens a themed `Dialog`: an `alertdialog` named `Itinerary PDF`.
  2. The dialog shows `Preparing your PDF…` (with `aria-busy`) while the blob builds.
  3. When the blob is ready, the dialog shows `Your PDF is ready.` with a **Download** button, which gets focus, and a Cancel button.
  4. The Download click calls `saveBlob` synchronously inside the handler, so the activation is fresh, then closes the dialog.
  5. On an error the dialog shows `Could not create the PDF. Try again.` with Try again and Close.
- **Scope:** the same dialog serves ExportControl and SharedTripView.
- **GPX:** Download GPX already calls `saveBlob` synchronously inside its click, so it gets no dialog. Google and Apple are links.
- **Chrome and Firefox:** these browsers download on the dialog's Download click, which is the same `saveBlob`. E2E specs click "Download PDF", then the dialog's Download (`exact: true`).
- **Honest limit:** Safari may still show its own prompt the first time per site. Record this in the C5 row and in the final report.
